# Какие данные понадобятся для реального применения

Этот перечень составлен по итогам анализа пробелов в публичных источниках и проверки синтетической модели. **Наличие источника не означает, что соответствующее поле уже получено**.

| Объект | Обязательные поля и единицы | Что проверяем | Приоритет |
|---|---|---|---|
| Грузовая заявка | `cargo_id`, `type`, `origin`, `destination`, `quantity_t`, `ready_at`, `due_at`, `critical_minimum_t` | Нет ли массы без места назначения, срок не предшествует готовности, план по категориям не смешивается с отдельными партиями | P0 |
| Речная сеть | `edge_id`, `from`, `to`, `length_km`, `direction`, `navigation_start/end` | Связность пути, единицы, возможность возвращения флота | P0 |
| Глубины | `edge_id`, `date`, `available_depth_m`, `source`, `observed_or_forecast` | Полнота `дата × участок`, сведения о фактических ограничениях и запасе под днищем | P0 |
| Судно/баржа | `vessel_id`, `capacity_t`, `draft_empty_m`, `draft_full_m`, `available_from/to`, `type` | Связь осадки с загрузкой, ограничения по массе, реальное наличие в регионе | P0 |
| Буксир и сцепка | `tug_id`, совместимые `barge_id`, допустимая тяга и условия плавания | Нельзя одновременно закреплять один буксир за двумя составами | P0 |
| Время рейса | Скорость вверх/вниз, погрузка/выгрузка, ожидание шлюзов/причалов, время возврата | Полный оборот ресурсов, а не только один прямой переход | P1 |
| Фактический рейс | `trip_id`, состав, пункты, масса, даты отправления/прибытия, простои и причины | Калибровка времени и сравнение с реальным диспетчером | P0 для внедрения |
| Экономика | руб./т, тарифы, топливо, складирование, перегрузка, зимник | Экономическая постановка и эффект на всём транспортном пути | P2 |
| Ограничения социальной доставки | Потребность в топливе, продуктах, медикаментах по пунктам и срокам | Не допустить выигрыш по углю за счёт недовоза жизненно необходимых товаров | P0 для внедрения |

## Обязательные правила очистки

- Различать **неизвестное** значение глубины и **закрытый** участок: нельзя считать отсутствие записи безопасной глубиной или автоматически записывать недовоз без предупреждения.
- Не переносить общеречные агрегаты на локальное плечо и не объединять публикации разных дат без определения совпадающей области учёта.
- Фактический уровень гидропоста не равен глубине переката или разрешённой осадке.
- Для каждой записи хранить источник, дату наблюдения, единицу и уровень доверия (`official`, `scenario`, `assumption`).
- Для каждого прогона сохранять версию алгоритма, схему JSON, конфигурацию, идентификатор сценария и ключ воспроизводимости.
- Результаты обучения ML по сценариям делить на train/test **группами исходных сценариев**, а не отдельными похожими рейсами.

## Что уже есть, чего нет

**Есть:** нормативы участков, отдельные публичные бюллетени, оперативная статистика по Яне в целом, справочники типов флота, синтетические таблицы, код симулятора и валидатор. **Нет подтверждения:** полного массива реальных заявок, состава флота именно на пилотном плече, ежедневной гидрологии всех участков и фактического базового расписания для сопоставления с алгоритмом.
