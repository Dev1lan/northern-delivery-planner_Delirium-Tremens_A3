# Математическая модель и результаты экспериментов

## Формализация

**Вход:** партии `i` с объёмом `q_i`, датой готовности `r_i`, крайним сроком `d_i`, категорией и пунктом назначения; составы с грузоподъёмностью, порожней/полной осадкой, временем доступности; граф речных участков с длинами, глубинами по датам и навигационными окнами. Партия может перевозиться частично в пределах правил симулятора.

**Допустимое назначение:** погрузка после `r_i`; достаточная вместимость; осадка состава не превышает доступное ограничение на каждом затронутом участке и дате; судно/буксир не используются параллельно; учитываются дорога, погрузка/выгрузка и обратный оборот флота; завершение до ограничения навигации.

**Критерий версии 2.1.0:** лексикографически максимизировать тройку

`(delivered_on_time_t, delivered_total_t, -completed_trips)`.

Сначала увеличивается доставленный вовремя тоннаж; при равенстве — общий; при равенстве двух критериев — уменьшается число рейсов. Это **не** минимизация затрат и не нормативная политика снабжения жизненно важными грузами.

**FCFS:** базовое обслуживание заявок в очередности готовности. **OPTIMIZED:** жадный выбор допустимых рейсов по качеству назначения и ограниченный локальный поиск; рассматривает подготовленные входы с заранее известными условиями сценария. Оба проверяются общим аудитором.

## Проверка гипотезы H1

*Одинаковая постановка:* 114 пар сценариев, исходные заявки, календарь глубин, навигация и флот идентичны для сравниваемых стратегий. Следовательно, измеряется эффект правил планирования *внутри модели*.

| Показатель | Итог (по сообщённой финальной сводке версии 2.1.0) |
|---|---:|
| Средний прирост своевременной доставки | **+8 410,333 т/сценарий** |
| Медианный прирост своевременной доставки | **+8 400,681 т/сценарий** |
| Средний относительный прирост | **+323,118%** — среднее процентов по 114 парам |
| Диапазон абсолютного прироста в срок | **+3 414,691…+12 619,495 т/сценарий** |
| Среднее изменение общего тоннажа | **+2 183,790 т/сценарий** |
| Сравнения, где OPTIMIZED лучше / равен / хуже по доставке вовремя | **114 / 0 / 0** |
| Аудит ограничений | **0 нарушений на 228 расписаниях** |
| Тесты после интеграции JSON-адаптера | **16 пройдено** |

**Важно:** здесь +323,118% означает `(1/114)·Σ[(Qopt_i−Qfcfs_i)/Qfcfs_i]·100%`, а не `(средний Qopt − средний Qfcfs)/средний Qfcfs`. Во всех 114 парах FCFS имел ненулевую своевременную доставку. Нельзя называть этот процент ожидаемым приростом реальной перевозки.

## Категории — отрицательный побочный результат

Средние значения на один сценарий:

| Категория | FCFS в срок, т | OPT в срок, т | FCFS всего, т | OPT всего, т |
|---|---:|---:|---:|---:|
| Уголь | 1 798,865 | 8 279,789 | 6 436,790 | 8 279,789 |
| Сырая нефть | 1 010,256 | 2 938,726 | 2 916,152 | 3 280,548 |
| Продовольствие | 0 | 0,939 | 22,587 | 0,939 |
| Дополнительное продовольствие | 0 | 0 | 1,956 | 0 |

Своевременный тоннаж вырос в основном на больших грузовых партиях, но общая доставка продовольствия сократилась. **Вывод:** задача на максимум тонн недостаточна для реального Северного завоза. Необходимы минимальные нормы по критичным категориям и получателям и выдача статуса «ограничения невыполнимы», если норматив обеспечить нельзя.

## Из чего возникает улучшение и что ещё нельзя заключить

Предполагаемый механизм: выбор более подходящей загрузки и последовательности рейсов при дефиците навигационного времени и флота. Для количественного объяснения конкретных замен рейсов нужны JSON-расписания одного сценария с событиями отправления/прибытия (прилагаются отдельно из `final_results/`). Большая разница с FCFS не означает такую же разницу с реальной диспетчерской практикой; дополнительно нужен baseline EDF и фактический baseline перевозчика.

Полная будущая информация о глубинах, заявках и закрытиях задана сценарно; прогноз реальной глубины и Monte Carlo **не реализованы**. Важно оценить устойчивость к ошибкам прогноза на следующем этапе.

## Как воспроизводить

1. Взять **финальный проект** `Case_a3` из `[ССЫЛКА_НА_GITHUB]`, версию ядра 2.1.0 и зависимости из README.
2. Запустить тесты, проверки сценариев и генератор/сравнение по документированным в репозитории командам.
3. Пересчитать одинаковые сценарии обеими стратегиями, сравнить `comparison_final.csv` и проверить аудитором допустимость.
4. Использовать `result_adapter.py`/`RESULT_CONTRACT.md` для JSON-результатов дашборда.

Архив `research_snapshot/` из данного комплекта — **не** замена финальным входным сценариям из проекта.
