# ТЗ на финальный этап: сеть рек Якутии

Цель финала — показать не одну Яну, а сеть рек Якутии. Суда перегоняются между реками через море, в расчёте есть деньги, у судов есть карточки, а свой датасет загружается и отображается без ручной подгонки.

Каркас уже работает на сетевом ядре `network/` 3.0.0 (контракт `result.v3.schema.json`): карта Якутии, синтетический сценарий, сайт с заглушками. Ниже — что нужно от команды, чтобы заглушки заменить настоящими данными и расчётами. Описание текущего состояния — `yakutia/README.md`.

## 1. Ядро (network 3.0.0)

Обязательно:

- **Допуск класса судна на ребро.** Сейчас речные суда выходят в море: в лучшем плане Т-201, Б-23 и Б-51 идут морем на Колыму.
  - Ребру нужно поле `allowed_vessel_classes`, например `["M-SP", "O-PR"]`; судну — поле `vessel_class`.
  - Проверка — в поиске пути (`network/routing.py`) и в аудиторе (`network/validator.py`).
  - Сайт уже помечает такие рейсы красным; после доработки пометок быть не должно.
- **Реальные данные.** Сейчас `parse_scenario` отклоняет всё, что не помечено `data_status = "SYNTHETIC"`. Нужно разрешить значения `REAL` и `MIXED`, причём источник данных должен сохраняться по каждой заявке и судну.
- **Таймаут и прогресс.** Сценарий Якутии считается около 5 с. Нужно понимать, сколько займёт в 2–3 раза больший сценарий, и какие пределы поиска (`limits`) рекомендовать по умолчанию.

Желательно:

- Перевалка: груз приходит в Тикси одним рейсом и уходит дальше другим, со связью «готовность второй заявки = выгрузка первой». Сейчас готовность задаётся датой вручную.
- Буксир может отдельно пойти за баржей в другой порт (сейчас пара собирается только в одном порту).
- Несколько партий груза в одном рейсе.

Формат результата v3 не менять. Если что-то добавляете, то только новыми полями, чтобы сайт не сломался.

## 2. Финансовое ядро

Сайт уже вызывает `network.financial.evaluate_schedule(result, tariffs)` и показывает итог, стоимость тонны, статьи затрат и сравнение стратегий. Нужно:

- **Вход.** Расписание v3 (поле `financial_inputs` содержит рейсы, км в грузу и порожнём, часы погрузки, выгрузки, ожидания, занятость каждого судна) плюс ставки.
- **Ставки с источником.** Топливо (₽/км или ₽/ч ходового времени по типу судна), фрахт или содержание судна в сутки, портовые сборы по портам, погрузка и выгрузка (₽/т или ₽/ч). Для каждой ставки — `source_status` и ссылка на источник.
- **Цена недовоза** по типу груза: доставка зимником или авиацией, ₽/т. Без неё нельзя сравнить «дорогой план с перегоном» и «дешёвый план с недовозом».
- **Выход.** JSON вида:

  ```json
  {"currency": "RUB", "total_cost": "...", "cost_by_item": {"...": "..."}, "cost_per_t_on_time": "...", "undelivered_penalty": "...", "source_status": "..."}
  ```

  Плюс разбивка по рейсам и по судам: на сайте она нужна для карточки судна.
- **Желательно.** Целевая функция «минимум стоимости при выполнении минимумов» как отдельная стратегия ядра. Сейчас поиск ведётся по тоннам, а деньги считаются после.

## 3. Данные о судах (карточки)

Нужно от того, кто знает, откуда брались суда:

- Источник: реестр (Российский речной регистр, РМРС), сайт пароходства, открытые таблицы; ссылка и дата выгрузки.
- Поля по каждому судну:
  - название и номер в реестре;
  - тип: буксир-толкач, баржа, танкер, самоходное;
  - проект и класс регистра («Р», «О», «О-ПР», «М-СП»);
  - год постройки и оператор;
  - мощность (л.с.), грузоподъёмность (т);
  - осадка порожнём и в грузу (м), скорость вверх и вниз (км/ч);
  - разрешённые грузы и порт базирования.
- Формат: CSV, одна строка на судно, с колонкой `source` для каждого поля или хотя бы для строки.
- Реальные суда не смешивать с синтетическими без пометки. Если судно реальное, а характеристики оценочные, это должно быть видно в колонке источника.

Что уже готово под эти данные: `data/yakutia/fleet_cards.json`. Поля `project`, `built`, `operator`, `registry_id` пока пустые.

## 4. Карта рек и геооснова

Готово: 6 рек, 24 порта, 23 участка, морские переходы Тикси → Нижнеянск → Чокурдах → Зелёный Мыс. Нужно уточнить:

- Список портов, которые точно должны быть на карте. Отдельно — нужны ли Оленёк, Анабар, Хатанга.
- Координаты портов, если есть точнее приближённых.
- Глубины и окна навигации по участкам. Сейчас глубины синтетические, по качественному описанию: межень в августе—сентябре, мелкая Яна и Вилюй, море открыто с 20 июля по 25 сентября. Если есть таблицы гарантированных глубин или даты навигации — передать их с источником.
- Длины участков по фарватеру. Сейчас они посчитаны по сглаженной линии Natural Earth и короче реальных.

## 5. Сайт и дизайн

Готово: карта сети на весь экран, шкала времени с анимацией, вкладки Обзор / Суда / Заявки / Реки / Финансы, загрузка своего JSON, страница Яны с прогнозом нейросети на `/yana`. Осталось:

- Подключить финансовое ядро вместо демо-ставок. Плашка «демо» должна пропасть.
- Подключить реальные карточки судов: фото и ссылку на реестр, если будут.
- В карточке судна — его стоимость за сезон из разбивки финансового ядра.
- Вкладка «Сравнение» с переключателем целевой функции, когда в ядре появится стратегия по деньгам.
- Режим для показа: заготовленный сценарий и кнопка «Показать сезон» с автопрокруткой и подсветкой ключевых событий (перегон, обратная загрузка, выход в море).

## 6. Загрузка чужих датасетов

Сейчас загружается только JSON в формате ядра. Нужно:

- CSV-набор: `ports.csv`, `edges.csv`, `depths.csv`, `fleet.csv`, `cargo.csv`, а также Excel с теми же листами. Шаблоны лежат на сайте.
- Распознавание колонок по синонимам («порт отправления», «from», «origin») и единиц измерения (т или кг, м или см, км/ч или узлы).
- Сопоставление названий портов с геоосновой: «Н.-Янск» → Нижнеянск. Неизвестные порты показываются схемой, с предупреждением.
- Перед расчётом — отчёт проверки на русском: строка, поле, что не так, как исправить. Сейчас сообщения ядра частично на английском.
- Пропуски в глубинах можно заполнять интерполяцией только с явной пометкой «восстановлено» в данных и на карте.

## 7. ML (ждёт ядро и данные)

- Генератор сетевых сценариев (разные порты, флот, заявки) и разметка ядром 3.0.0: примерно 1–2 тыс. сценариев, около 3 ч на одном ноутбуке.
- Модель предсказывает долю груза в срок и выигрыш от перегона до расчёта. Это помогает решить, нужен ли дорогой поиск с перегоном и какие пределы поиска ставить.
- ML на приёме данных: распознавание колонок, сопоставление портов, поиск выбросов. Расчёт после этого всё равно делает ядро.
- ML не заменяет расчёт там, где ядро не считает: правильных ответов для проверки там нет. Для слишком больших сценариев допустима только быстрая оценка с интервалом, подписанная как оценка.

## 8. Контракты

- Вход ядра: JSON в формате `data/network_demo/*.json` и `data/yakutia/yakutia_network.json`.
- Результат: `result.v3.schema.json`, менять только добавлением полей.
- Тарифы: формат `data/yakutia/tariffs_demo.json` до появления финансового ядра; новый формат — с примером файла.
- Суда: CSV из раздела 3.
- Любой новый файл данных — с полем источника и статусом `SYNTHETIC`, `REAL` или `MIXED`.

## 9. Приёмка

- Сценарий Якутии считается на сайте не дольше 30 с, все расписания проходят аудит ядра.
- Ни одно речное судно не выходит на морское ребро.
- Финансы считаются по ставкам с источником, плашки «демо» нет.
- У каждого судна в сценарии есть карточка; у реальных судов заполнены поля реестра с источником.
- Чужой датасет в CSV или Excel загружается без ручной правки, или пользователь получает понятный отчёт, что исправить.
- Страница Яны с ML работает как раньше; контракт 1.0.0 проходит проверку на 109 сценариях.
