# Сетевое планирование речных перевозок 3.0.0

Планировщик хранит место и время доступности каждого буксира и каждой баржи. После выгрузки состав остаётся в порту назначения. Например, один состав последовательно везёт 100 т из A в B, выгружает, загружает 80 т в B и везёт их в C. Если заявка идёт сразу из A в C, тот же граф допускает переход через B с грузом на борту и разгрузку в C.

## Запуск и повтор эксперимента

Проверенная среда — CPython 3.12.14. Одиночный запуск использует стандартную библиотеку, для тестов и сравнения установите зависимости `requirements.txt`. Команды выполняются из папки `Case_a3`.

```powershell
python -m network data/network_demo/c_reposition_chain.json --output results/network_chain.json
python -m experiments.run_network --replan-demo --output results/network_demo_run
python -m unittest discover -s tests -p 'test*.py'
```

Для своих входов повторяйте `--scenario <путь к JSON>` и `--strategy <имя>`. Передайте `--limits <JSON>` для настройки поиска. Runner сохраняет исходные снимки, параметры, хэши файлов, версию Python, результаты, `metrics.csv` и `comparison.csv`. Он проверяет каждый результат по `result.v3.schema.json` и повторно проигрывает расписание. Для повторного опыта возьмите файлы из `inputs/`, прежние стратегии и параметры из `manifest.json` и укажите новый путь вывода. Время вычисления в CSV зависит от среды и нагрузки.

Входные примеры `data/network_demo/` описывают условные порты A, B, C и D, флот, заявки и физику. `daily_conditions` уточняет базовые условия ориентированного ребра по календарному дню. Доступность проверяется на каждом дне, затронутом переходом. Для ожидания разрешены порты. Время задаётся без смещения часового пояса, тоннаж обрабатывается целыми килограммами.

## Как выбирается перегон

| Стратегия | Правило |
|---|---|
| `NETWORK_FCFS` | Порядок готовности заявки, затем идентификатор и доступность состава |
| `NETWORK_GREEDY` | Приоритет своевременного груза и производительности рейса |
| `NETWORK_SOCIAL` | Поиск плана с выполнением минимумов и лучшим тоннажем среди местных назначений |
| `NETWORK_REPOSITION` | Тот же поиск с порожними переходами к заявке и продолжением работы из новых портов |
| `NETWORK_RETURN_EMPTY` | Диагностическая стратегия с обязательным порожним возвратом после выгрузки |

Перед перегоном проверяется маршрут до порта погрузки и возможность выполнить связанную доставку вовремя. Затем поиск сравнивает цепочки целиком, включая следующие доступные заявки в порту назначения. Порожний переход принимается только в расписании, которое строго улучшает оценку по сравнению с найденным планом `NETWORK_SOCIAL`. При равенстве выигрывает план без перебазирования. Приоритеты идут по порядку: выполнение минимумов, тонны вовремя, тонны всего, меньший порожний пробег, меньше рейсов. Если полного обеспечения найти не удалось, сначала сравнивается число невыполненных минимумов, затем суммарный дефицит.

Поиск перебирает назначения, размеры загрузки, пути и порядок заявок в заданных пределах. Дополнительный локальный поиск перестраивает несколько хвостов расписания с другим первым назначением. Лимиты задают число расширяемых состояний и действий, число кандидатов и путей, длину пути и число дней ожидания. `SEARCH_LIMIT` указывает на исчерпание бюджета действий или расширений. `SEARCH_FINISHED` означает завершение в рамках заданной ширины и правил поиска. Оба статуса описывают эвристику с ограниченным набором рассмотренных вариантов.

## Проверка и JSON v3

`network.validator` заново проигрывает расписание, проверяет порт каждого ресурса, время, маршрут, глубины, осадку, готовность заявки, грузоподъёмность, баланс масс и занятость. Отчёт об ошибке указывает рейс и причину. В v3 есть параметры исходного графа, заявки, отпечаток входа, события, финальные порты судов и финансовые величины. `network.adapter.audit_result` повторно проверяет сохранённый результат, включая события и производные показатели. В `reposition_comparison` записаны измеренные разницы с местным планом и основание выбора.

Физический аудит и социальное обеспечение проверяются отдельно. Минимум засчитывается после выгрузки. Требования агрегируются по группам типов грузов по всей сети. `FEASIBLE` означает найденный допустимый план с выполненными минимумами. `UNKNOWN` означает дефицит без доказательства невозможности. Для `INFEASIBLE` нужна достаточная оценка, например общий объём подходящих заявок меньше заданного минимума. Форматы v1/v2 относятся к линейному ядру.

## Финансовая оценка

`financial_inputs` включает порты и ресурсы рейсов, километры в грузу и порожнём, транспортную работу, секунды движения, ожидания и обработки, занятость и простой ресурсов, недовоз, просрочку и дефицит. `network.financial.evaluate_schedule(result, tariffs)` оценивает уже проверенное расписание. Можно передать `--tariffs <JSON>` при запуске. Укажите `currency`, `source_status` и ставки для `loaded_km`, `empty_km`, `loading_hour`, `unloading_hour`, `waiting_hour`, `tug_busy_hour`, `barge_busy_hour`. Для отсутствующего тарифа возвращается ошибка. Нулевая ставка должна быть явной. Подбирайте статьи так, чтобы не удваивать расходы. Финансовая оценка описывает стоимость по этим ставкам, поиск рейсов использует нефинансовую цель.

## Перепланирование

`network.replanning.replan(previous, revised_raw, as_of, ...)` принимает проверенный предыдущий JSON v3, пересмотренный сценарий и момент отсечения. Дополнительно можно передать `resource_updates` по идентификаторам, а также `delivered_t` и `remaining_t` по заявкам для сверки фактических данных. Поля `current_port` или `edge_id` сверяются с журналом. `available_at` может задержать готовность к следующему рейсу. Выполненные и начатые рейсы сохраняются, их масса резервируется, а оставшаяся часть получает собственный результат и аудит. При физически небезопасном изменении начатого маршрута возвращается `REQUIRES_INTERVENTION` с причиной. Планировщик оставляет решение о перенаправлении уже движущегося состава диспетчеру.

В примере H после доставки 100 т A → B участок B → C закрывается. Состав остаётся в B, готовность буксира сдвигается на 04:30. Новый план отправляет 35 т срочного груза B → D. Ранее доставленные 100 т остаются в журнале, а 80 т B → C остаются в остатке.

## Результаты синтетических проверок

| Опыт | Результат |
|---|---|
| A. A → B → C | Один состав доставляет 180 т вовремя, 0 км порожнего пробега и конечный порт C |
| B. Обратная загрузка | 180 т вовремя и 0 км порожнего хода против 100 т и 10 км при обязательном порожнем возврате |
| C. Перегон с продолжением | 180 т вовремя против 50 т без перебазирования. Состав проходит C → B → A порожняком, затем A → B → C с двумя грузами. Порожний пробег 22 км |
| D. Поздний или равнозначный перегон | Местный состав доставляет 40 т вовремя, порожний пробег 0 км. Тест проверяет и слишком долгий подход, и равный результат после ускоренного подхода |
| E. Социальный конфликт | Тоннажная стратегия даёт 100 т вовремя при дефиците продовольствия 30 т. Социальная доставляет 30 т и закрывает минимум. Поиск с перегоном даёт 58,333 т вовремя при том же выполненном минимуме |
| F и G. Запреты и общие ресурсы | Мелководье и отсутствие пути дают 0 т. Общий буксир исключает одновременное выполнение двух заявок |

Граф, флот и заявки синтетические. Данные показывают поведение алгоритма при заданных условиях. Оценка для реальной Яны требует подтверждения портов операций, календарей, направлений, характеристик судов, загрузки и тарифов. В одном рейсе моделируется одна партия, допускаются частичные отправки. Составы выбираются из явно совместимых пар в одном порту. Самостоятельное перемещение буксира для подбора баржи, одновременная перевозка нескольких партий и точный оптимум требуют отдельной модели и проверки.
