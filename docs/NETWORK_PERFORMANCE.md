## Профиль исходной версии

На сценарии B без профилировщика первый замер занял 15,36 с. Под cProfile поиск расписания занял 32,78 с, генерация вариантов рейса — 32,50 с, маршрутизация — 31,92 с за 32 420 запросов. Поиск даты выхода вызван 480 885 раз. Проверка проходимости вызвана около 1,41 млн раз. Подбор загрузки вызван 7 081 раз и занял 27,37 с с учётом вызванных функций. Перебор кандидатов вызван 176 раз, создано 1 004 состояния. Вычисление ключей и сравнение состояний занимали существенно меньше времени, чем генерация маршрутов. Времена вложенных функций пересекаются.

## Изменения

- Календарь хранит интервалы одинаковых дневных условий. При первом непроходимом интервале в ходе перехода поиск перескакивает к его окончанию, сохраняя действующий предел ожидания. Проверяются все дни, затронутые переходом, включая смену глубин после полуночи. Независимый аудитор использует прежнюю проверку.
- Динамический кеш маршрутов принадлежит одному расчёту и ограничен 8 192 записями. Ключ включает начало и конец, время, крайний срок, осадку и подпись разрешённых рёбер с точными длительностями перехода. Подпись вычисляется после индивидуальной проверки допусков пары. Календарь, настройки и условия сценария принадлежат экземпляру маршрутизатора.
- До симуляции рейса проверяются совместимость, местоположение и доступность, остаток груза, достижимость по допущенным рёбрам и оптимистичная нижняя оценка времени по графу. Индекс грузов по барже и порту используется в локальных стратегиях. Для порожнего подхода нижняя оценка включает оба плеча. Окно, в которое переход не может поместиться даже без ожидания, исключается.
- Кеш готовых рейсов ограничен 16 384 записями. Учитывает исходный порт и готовность состава, груз, загрузку, дефицит минимума, политику движения и брони причалов обоих портов. Эквивалентность пары требует одинаковой проходимости по графу, длительности рёбер, крайнего времени доступности, осадок, вместимости, скорости грузовых операций и класса баржи для причалов. Физические ID восстанавливаются до оценки тарифа и записи в расписание.
- В генерации рейсов сохраняются только лучшие кандидаты по прежнему порядку. Поиск сохраняет существующий ключ состояния с местами и временами доступности судов, остатками, дефицитом и бронями. Диагностика считает дубликаты и состояния, отброшенные шириной поиска.
- Опциональное сокращение предварительно ранжирует пары по доступности, нижней оценке времени, сроку, ориентировочной загрузке и вкладу в минимум. При ограничении пар на груз сначала представлены разные комбинации классов. Поля `top_k_pairs_per_cargo`, `max_candidates_per_state` и `max_detailed_checks_per_iteration` по умолчанию отключены. Два общих лимита считаются на генерацию вариантов одного состояния, применяется более строгий из заданных.

## Бюджет времени

`SearchPolicy(mode="FAST")` задаёт 5 с, `DEMO` — 30 с, `STANDARD` — 120 с. В `RESEARCH` бюджет задаётся через `time_seconds`, без него поиск ограничен существующими структурными лимитами. По `TIME_LIMIT` возвращается найденный план или пустое расписание, если рейсы построить ещё не успели. По завершении ядро проводит независимую проверку. Сериализация и аудит могут добавить время сверх бюджета поиска. `KeyboardInterrupt` распространяется наружу. Статус выполнения социальных минимумов остаётся независимым от причины завершения.

Существующий вызов без `search_policy` сохраняет прежнюю форму v3. Явный `SearchPolicy()` добавляет `search_diagnostics` с замером и счётчиками, не включает отсечение и ограничение времени. Замеры длительности зависят от нагрузки. Выбор расписания без ограничения времени детерминирован на проверенных входах.

### Настройки

- Для воспроизведения исторических результатов используйте исходные `Limits`, оставляя три опциональных ограничения выключенными. Если нужен запас времени, задайте `STANDARD` или собственный `RESEARCH`-бюджет.
- Для интерактивной демонстрации на полном сценарии проверены `DEMO`, 8 пар на груз и 64 подробных проверки на состояние. На C получено 47 182,634 т за 2,53 с, на D — 46 759,579 т за 25,02 с. Отбор изменяет результат ограниченного поиска. В D выросли своевременный тоннаж и порожний пробег. Эти числа относятся к входной модели и проверенному расписанию.
- `FAST` подходит для получения раннего результата. На D он вернул `TIME_LIMIT` с 7 236,587 т в срок и 7 рейсами примерно за 5,17 с. Дальнейший поиск может дать другой план.

## Параллельный запуск пакета

```powershell
python -m experiments.run_network --scenario other_data/benchmark/yakutia_real_full.json --limits other_data/benchmark/limits.json --strategy NETWORK_REPOSITION --strategy NETWORK_SOCIAL --workers 2 --output results/network_parallel
```

`--workers` задаёт число отдельных процессов. По умолчанию используется последовательный режим. Единица работы — один сценарий с одной стратегией. Каждый процесс считает расписание со своим кешем. Результаты сохраняются в исходном порядке, а перед экспортом проходят проверку схемы и независимый аудит. Для одного задания пул не создаётся. В `metrics.csv` поле `compute_seconds` показывает время работы над отдельным планом. Для оценки ускорения пакета измеряйте полное время команды.

Для вызова из Python используйте `network.batch.run_jobs`:

```python
from network.batch import PlanningJob, run_jobs

if __name__ == "__main__":
    jobs = [
        PlanningJob(scenario, "NETWORK_SOCIAL"),
        PlanningJob(scenario, "NETWORK_REPOSITION"),
    ]
    results = [run.result for run in run_jobs(jobs, workers=2)]
```

`scenario` — уже загруженный словарь входного сценария. Каждый `PlanningJob` может получить свои `limits`, `tariffs` и `search_policy`. Временной бюджет применяется к каждому поиску отдельно. При остановке по времени выбор промежуточного плана зависит от нагрузки. Python-вызыватель может повторно проверить результат через `network.adapter.audit_result`, как это делает команда экспорта.

На контрольном пакете из четырёх расчётов (сценарии C и D, стратегии `NETWORK_REPOSITION` и `NETWORK_SOCIAL`) один процесс занял 26,91 с, два — 20,17 с, четыре — 26,09 с. Это один замер на конфигурацию. На такой нагрузке два процесса дали примерно 1,33×, а время отдельного плана D по-прежнему определяло время пакета. Полные JSON четырёх расчётов совпали. В отдельной проверке побайтово совпали 40 экспортированных расписаний и отчёт перепланирования. Полный набор прошёл: 90 тестов.
