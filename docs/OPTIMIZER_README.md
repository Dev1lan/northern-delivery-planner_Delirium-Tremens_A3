# Оптимизация сценарных речных перевозок

`optimizer.py` строит допустимое расписание для заранее известных заявок по одной линейной цепочке участков. `OPTIMIZED` — воспроизводимая эвристика, а не математически точное решение. Источники, исходные CSV и старые отчёты сохранены; см. `optimization_report.md` для результатов нового эксперимента.

## Запуск

```powershell
python -m unittest discover -s tests -p "test*.py" -v
python -m experiments.tiny_exact
python optimizer.py --out results_new
python optimizer.py --candidate-limit 20 --out results_limit20
python -m experiments.run_final_experiments
python -m experiments.run_extended_experiments
python -m experiments.verify_final_reproducibility
python -m experiments.write_optimization_report
python validate.py --skip-reproducibility
python generate.py --out regenerated_validation_data
python validate.py --out regenerated_validation_data
```

Ноль или отсутствие `--candidate-limit` означает просмотр всех подходящих партий; положительный параметр ограничивает их число на состав и день. Через Python тот же параметр можно задать полем сценария `candidate_limit` (`None` — без ограничения). Файлы в `data/` не пересоздаются командами оптимизатора. `validate.py --skip-reproducibility` проверяет сохранённый архив; полную проверку воспроизводимости исправленного генератора нужно выполнять для заново созданного каталога. Старый архив рейсов и его манифест намеренно не перезаписаны: исправление симулятора меняет производные CSV.

## Постановка

Эксперимент — **планирование при полной информации о заданном сценарии**, не прогноз реального диспетчера. До начала расчёта обеим стратегиям передаются все партии, их объёмы, даты готовности и сроки, флот и его доступность, а также точные ежедневные глубины и закрытия на всём горизонте. При выборе в конкретный день OPTIMIZED рассматривает партии, готовые до его конца, и может ждать их появления; FCFS использует простое правило очереди. Обе стратегии проверяют будущие условия по всем дням потенциального рейса. Поэтому сравнение показывает преимущество правила планирования внутри сценария при точном знании будущей навигационной обстановки, а не качество её прогноза. Входные глубины и заявки синтетические или предположительные. Времена — наивные ISO с единой временной базой входа.

Лексикографическая цель: сначала максимум `delivered_on_time_t`, при равенстве максимум `delivered_total_t`, затем минимум `completed_trips`. Допустимые поздние рейсы сохраняются: их глубины, окна, готовность груза и занятость ресурсов проверяются тем же аудитором. Жадное ранжирование и до двух локальных улучшений — эвристика, а не гарантия нахождения лексикографического оптимума. Приоритет типа груза отдельно в цель не входит.

## Алгоритм и ограничения

На каждом шаге для пар состав–партия строятся кандидаты. С помощью общей функции `best_load` ищется наибольшая допустимая загрузка с шагом 0,001 т: проверяются границы смены календарного дня, глубин/осадки и окончания доступности. Проверка не предполагает, что допустимость монотонна по массе: более долгая обработка может изменить дни прохождения. Затем ранжируются кандидаты по признаку своевременности, тоннам в срок на час оборота и массе. После жадной сборки выполняются до двух локальных улучшений с аудитом. Это ограниченный поиск, не гарантирующий глобальный максимум.

Модель проверяет грузоподъёмность, индивидуальную доступность состава, готовность груза, продолжительность обработки и пути, осадки баржи и буксира, условия участков по дням, возвращение и занятость каждого ресурса. Валидатор проверяет сформированные рейсы по тем же сценарным правилам. Модель не проверяет физическую пригодность судов к реальному рейсу; фактические сведения о флоте, глубинах и заявках отсутствуют. Причалы как общий ресурс, лёд, ветер, разрешения, смена маршрута и буксировочная мощность не моделируются.

Пусть D — число дней, U — число составов, C — число доступных партий, R — число назначенных рейсов, S — число участков, B — число рассматриваемых границ изменения допустимости. Кандидатный поиск в худшем случае требует порядка `O((D + R) * U * C * B * S)` проверок участков; B зависит от числа затронутых дней. Ограничение кандидатов заменяет C на заданный лимит после сортировки. Локальный поиск может дополнительно рассматривать `O(R²)` пар и выполнять полный аудит предложения; практическое время зависит от числа проверяемых дат и структуры расписания. Значения времени в CSV измерены на локальном запуске, не являются гарантией скорости.

После обоих экспериментальных скриптов `results/comparison_final.csv` содержит парные метрики, `results/ml_scenario_results.csv` — результат по видам груза, `results/final_results/` — отдельные рейсы и JSON, `results/candidate_limit_results.csv` — проверку лимита, `results/tiny_exact_results.csv` — малые задачи. Манифест `results/final_results/input_hashes.json` фиксирует SHA-256 использованных входов. Для одинакового кода и входа воспроизводятся расписания и показатели; время выполнения изменяется между запусками.

Версия алгоритма и хэши исходников зафиксированы в `ALGORITHM_VERSION.json`; это файловая фиксация, поскольку папка проекта не является Git-репозиторием. Итоговые CSV и `results/reproducibility_check.json` относятся к этой версии.
