# Перевалка и стоимость запланированных операций

## Финансовый контракт v3

В новых результатах с тарифами v2 `financial_evaluation.cost_basis = PLANNED_OPERATIONS`. Поле `total_cost` суммирует топливо, эксплуатацию, порожние переходы, обработку, портовые сборы и явно тарифицированную перевалку. `estimated_undelivered_cost` показывает условную оценку остатка по `alternative_delivery`. Поле `unpriced_undelivered_t` указывает остаток, для которого нет ставки. Оценка остатка исключена из суммы, стоимости на тонну и целевой функции. Отдельного тарифа привлечения флота в этом контракте нет.

Старые JSON v3 с `undelivered_penalty` и без `cost_basis` проверяются по исторической формуле. Ядро сравнивает денежные показатели в режиме «Что, если?» при одинаковой базе расчёта и одинаковых тарифах. Новый контракт и прежние результаты отличаются финансовым смыслом, поэтому клиенту следует проверять `cost_basis`.

`NETWORK_COST` сохраняет своевременный и общий тоннаж опорного плана и достигнутый уровень по каждому социальному минимуму. При невозможном или пока не выполненном минимуме экспортируются фактические статус и дефицит. Среди подходящих вариантов приоритет имеет меньшая стоимость запланированных операций. После равенства цены используются действующие критерии доставки, порожнего пробега и числа рейсов. Подготовка опоры занимает до 75% временного бюджета. Опора формируется поиском с перегоном либо передаётся через `--initial-plan`. Финансовый поиск ограничен лимитами кандидатов, маршрутов и времени.

## Вход терминала

`transshipment_ports` — словарь по имени порта. Каждый включённый терминал требует явно описанного причала в `port_operations`. Пример для синтетического порта B:

```json
{
  "transshipment_ports": {
    "B": {
      "cargo_types": ["coal"],
      "directions": ["RIVER_TO_SEA", "SEA_TO_RIVER"],
      "handling_seconds": 600,
      "storage_capacity_t": 80,
      "transfer_cost_per_t": 3,
      "currency": "DEMO"
    }
  }
}
```

Грузовые операции используют окна, скорости, классы, глубины и брони причалов. `handling_seconds` задаёт дополнительную задержку готовности партии между выгрузкой и погрузкой. Если физическая вместимость склада неизвестна, сценарий может явно принять `storage_assumption: "UNLIMITED"`. Груз занимает склад от завершения выгрузки до окончания следующей погрузки. Ставка перевалки необязательна. Если ставка задана, её валюта должна совпадать с тарифами v2. Типы груза явно разрешаются терминалом, причалом и баржой. Условная инфраструктура для сухих грузов не даёт допуска нефтепродуктам.

## Поиск и независимый аудит

Одна партия поддерживает два последовательных рейса с одним промежуточным терминалом. Для нескольких партий одной заявки строятся отдельные цепочки. Планировщик использует существующий симулятор рейсов, маршрутизатор, расписание занятости и лимит числа предложений. Поиск сначала строит прямой план, затем пробует добавить полные цепочки к его состоянию. При ограниченном времени `NETWORK_REPOSITION` резервирует до 20% бюджета для перевалки. `NETWORK_COST` также проверяет отдельные цепочки в ценовой фазе. При отсутствии терминалов прежний поиск не получает дополнительную фазу. Для сравнения используется `--disable-transshipment`.

Аудит связывает этапы по `batch_id`, проверяет два уникальных этапа, исходную заявку, одинаковую массу, разрешённое направление и терминал. Потом повторно проигрывает суда, рёбра, погрузку и выгрузку по времени, проверяет доступность груза, общий баланс заявки и одновременный остаток на складе. В социальные минимумы, доставленный тоннаж и знаменатель стоимости тонны входит только выгрузка в конечном порту. Оба плеча входят в расходы, занятость и пробег.

В JSON у рейсов есть `batch_id`, `stage` и `transfer_port`. В событиях доступны `batch_id` и `stage`. `transshipment_batches` показывает номера обоих рейсов, массу, сроки хранения, конечную выгрузку и состояние партии. Стоимость этапов хранится в `cost_by_voyage`. Если для использованного терминала задан тариф, отдельная сумма доступна в `transshipment_cost` и уже входит в `total_cost`.

Поиск эвристический. Сейчас он исследует одну перевалку с разными составами и одинаковой массой на обоих плечах партии. Частично выполненная цепочка не публикуется. Поиск может пропустить улучшение, если оно требует переназначения уже занятых судов или двух терминалов. Оперативное перепланирование уже начатых партий отклоняется явно. Дополнительная задержка хранения не моделируется как отдельный календарь оборудования.

## Воспроизведение

```powershell
python -m unittest tests.test_transshipment
python -m experiments.compare_transshipment path/to/sea_experiments.py --output results/transshipment_reference
python -m experiments.compare_transshipment path/to/sea_experiments.py --terminal-overlay path/to/tiksi_assumption.json --output results/transshipment_tiksi
```

Скрипт использует версии E0/E1/E2 из архива экспериментов Павла `aa174b0`. Внутри каждой пары он проверяет совпадение отпечатка сценария и использует одни тарифы, лимиты и флот. Для каждого плана экспортируются расписание, доставленный объём по заявкам, состав флота и финансовые статьи. Входы E0/E1/E2 сами по себе не содержат описания перевалочных терминалов. Дополнительный вариант Тикси явно задаёт условный причал 100 т/ч для угля, продовольствия и генгруза, неограниченное хранение и нулевую дополнительную задержку. Отдельная ставка не задана. Допущение одинаково для прогонов с выключенной и включённой перевалкой.

В синтетическом тесте груз 150 т нельзя доставить одним составом. С явным терминалом ядро доставляет весь объём двумя партиями, 80 и 70 т. Стоимость перевалки по заданной ставке составляет 450 DEMO. При более дешёвом физически допустимом прямом рейсе `NETWORK_COST` сохраняет прямой маршрут. Независимый аудит проверен на ранней загрузке, повторном этапе, конфликте судов, переполнении склада и превышении объёма заявки.

Исходные опубликованные входы, бюджет до 45 с на прогон, одинаковые тарифы и лимиты внутри каждой пары. Во всех шести прогонах аудит `PASSED`, остановка `TIME_LIMIT`, перевалочных партий 0. Терминалы в этих сценариях отсутствуют. Выделение времени на поиск перевалки не производится.

Тикси на данном графе связан с Быковым Мысом и Нижнеянском морскими рёбрами. Нет примыкающего речного ребра, поэтому терминал в Тикси сам по себе не стыкует чисто речное плечо с морским. В финальной версии такой терминал отсекается до выделения бюджета. Обе политики дали одинаковые расписания при фиксированном числе действий и состояний для E0, E1 и E2. Для практической настройки терминалов нужны подтверждённые грузовые операции, режим работы, вместимость и параметры флота. Условные допущения о причалах не заменяют эти данные.

122 теста прошли, архивный финансовый JSON с прежней формулой независимо аудируется. База реализации — `16d1554`. На синхронизированной ветке `origin/data/sea-experiments` (`b32db35`) код ядра совпал с базой. Отдельная ветка `origin/economics` рассчитывает линейный сценарий Яны и не содержит модели сетевой перевалки.


### Условный терминал в Быковом Мысе

Для проверки стыка добавлен отдельный внешний набор допущений: один совместный причал 100 т/ч для сухих грузов, хранение UNLIMITED, дополнительная задержка 0, отдельный тариф отсутствует. География рёбер, флот, заявки и исходные тарифы сохранялись. Этот же профиль причала присутствовал в обоих прогонах. Допущение не представляет подтверждённую инфраструктуру.

В повторном E0 доставлено 537 964,866 т в срок против 536 952,866 т без перевалки. Прирост целиком составила одна партия **1 012 т угля Z005, Джебарики-Хая → Быков Мыс → Нижнеянск**. Результат прошёл независимый аудит. Недовоз сократился до 191 930,134 т. Расходы по заданным ставкам выросли с 1 063 420 664,29 до 1 076 815 933,18 ₽. Отдельная ставка перевалки в этом эксперименте не задана. Поиск завершился за 37,18 с, контрольный прогон за 45,47 с. В первом пробном прогоне вместо угля была найдена партия 140 т продовольствия. Выбор при временном бюджете чувствителен к ходу поиска.

В каждой паре появился один перевалочный груз из двух рейсов. Для E1 это 140 т продовольствия Z063 из Нижнего Бестяха в Тикси, для E2 — 140 т продовольствия Z060 из Нижнего Бестяха в Зырянку. Все шесть расписаний прошли проверку схемы и независимый аудит. Прямые прогоны остановились по `TIME_LIMIT`, прогоны с перевалкой — по `SEARCH_LIMIT`. Эти единичные замеры не устанавливают ускорение. На этом сценарном терминале эффект перевалки не компенсировал разрыв между E1 и E2 по морскому тоннажу.

Файл допущений для воспроизведения — `experiments/bykov_transfer_assumption.json`. Передайте его через `--terminal-overlay`. В каждой паре проверяется одинаковый отпечаток входа. Отдельная ставка перевалки отсутствует, поэтому в стоимости учитываются предусмотренные тарифами рейсы и портовые операции обоих плеч.
