# Распределение морского флота

## Исходная версия

Ветка `feature/sea-fleet-allocation` основана на `568e0a1` (`fix/network-undelivered-cargo`). Перед работой выполнен `git fetch origin --prune`. Исходная ветка совпадала с удалённой. Контрольные эксперименты взяты из `origin/data/sea-experiments`, коммит `aa174b0`. Расчётные файлы этой ветки совпадали с базой. Эксперимент E1 уже включает модельное углубление и шесть Р-153. Все три сравниваемых варианта используют этот же флот и исходные ограничения E1.

## Причина и изменение

Текущий ранг сначала учитывает вклад в обязательные минимумы и своевременность, затем для `NETWORK_REPOSITION` сравнивает тонны в час. Короткий речной рейс крупного морского состава выигрывает у длинного морского. Если верх списка заполнен похожими речными вариантами, при малой ширине поиска морской вариант может не попасть в продолжение. Поле `priority` заявки само по себе этот конфликт не разрешает. В `NETWORK_COST` также участвует цена рейса, а ограничение по опорному тоннажу действует на уровне плана.

Опциональная политика `SearchPolicy(sea_fleet_allocation=True)` применяется в `NETWORK_REPOSITION` и `NETWORK_COST`. Она строит совместный начальный план речных и морских рейсов, затем запускает обычный поиск по расписаниям. `NETWORK_SOCIAL` сохраняет свою логику. Без флага поиск использует исходный порядок.

- Специализация выводится из реально допущенных пар на морских рёбрах. ID и название проекта судна не участвуют в решении.
- Для каждого состояния анализируются уже построенные физически допустимые морские рейсы и обычные речные альтернативы. Учитываются совместные ID ресурсов, возможность собрать пару в нужном порту, нижняя оценка времени подхода, остаток по дедлайну и время до конца текущего морского окна.
- Риск для морского рейса уменьшается, если есть независимая альтернативная пара. Потенциально потерянный морской объём сопоставляется с речным объёмом, который обычный состав не покрывает.
- Для заявки, у которой в графе нет пути целиком по реке, дополнительно учитывается своевременный морской вариант и остаток заявки с поправкой на запас времени. Это эвристическая оценка следующего назначения. Она не доказывает, сколько повторных рейсов поместится в сезон.
- Порядок учёта социальных минимумов, независимый аудит, физические правила и тарифный расчёт сохранены. Ограничения на осадку, окна и занятость проверяет существующий симулятор. Р-153 может выполнять речные рейсы, когда они выигрывают по оценке.

## Воспроизведение

Из корня ветки, с копией опубликованного скрипта и его исходных данных:

```powershell
python -m experiments.compare_sea_allocation path/to/data/yakutia_real/sea_experiments.py --seconds 45 --output results/sea_allocation
```

Скрипт сохраняет три расписания и `comparison.json`, сверяет отпечаток E1 и независимо аудирует каждый результат. У E1P исходная реализация Павла делит 45 секунд на два прохода. Фактическое время может быть меньше, если один из проходов остановился по собственным лимитам. У стратегии с флагом тот же максимальный бюджет. Временные замеры зависят от нагрузки, поэтому отдельные числа следует трактовать как наблюдение.

Для CLI нового ядра флаг называется `--sea-fleet-allocation`. Для повтора конфигурации из этого эксперимента передайте также `--recover-undelivered --mode RESEARCH --time-seconds 45`, исходные `--limits` и `--tariffs`. В отчёте `sea_opportunity_adjustments` считает поправки для конкурирующих вариантов, а не число предотвращённых конфликтов.
